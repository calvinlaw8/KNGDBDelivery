## 1.2 MySQL 首次失败诊断与修复补充

MySQL 阶段首次失败日志为：

```text
Automation_Script/Deploy/.runtime/logs/deploy-20260831-145117-MySQL_8.4.11_GTID______Keepalived_VIP.log
```

失败任务是 `mysql/02_configure.yml` 中使用临时 root 密码执行“修改 root 密码”。在不回显密码的只读诊断中确认：`10.20.14.50` 的 `mysql.service` 为 `active`，TCP `3306` 正常监听，数据目录已初始化，但 `/tmp/mysql.sock` 不存在。由此确认失败根因为客户端固定连接不存在的 Unix socket，不能归因于离线安装包、临时密码值或 mysqld 启动失败。

已将 `mysql/02_configure.yml`、`mysql/03_replication.yml` 和 `mysql/05_verify.yml` 的 MySQL 客户端调用统一改为显式本机 TCP：`--protocol=TCP --host=127.0.0.1 --port={{ mysql_port }}`，并保留敏感任务的 `no_log: true`。修复后三个 Playbook 的 Ansible 语法检查通过，客户端调用中不再残留 `--socket=/tmp/mysql.sock`。随后真实定向复验确认三节点 mysqld 和 Keepalived 均为 `active`，Replica 两侧 IO/SQL 线程均为 `Yes`，`Seconds_Behind_Source=0`，VIP `10.20.14.59` 可达，三节点及 localhost recap 均 `unreachable=0 failed=0`。

## 5. RabbitMQ 锁竞争与配置失败证据

失败目标：数据库节点 `10.20.14.46`

失败任务执行命令：

```text
dpkg -i /tmp/rabbitmq/*.deb
```

非敏感错误摘要：

```text
dpkg: error: dpkg frontend lock was locked by another process with pid 3748
```

失败后通过非交互 SSH 检查 PID、锁占用和 `dpkg --audit`：PID `3748` 已退出，无当前锁占用，审计无输出。未删除锁文件。随后在 RabbitMQ 安装 playbook 增加最多 5 分钟的实际锁占用等待，定向重跑已证明三节点都完成安装，锁问题已解决。

安装完成后，RabbitMQ 配置阶段的非敏感错误摘要为：

```text
10.20.14.44: BOOT FAILED / timeout_waiting_for_leader
10.20.14.45: Khepri has timed out on node rabbit@T-RabbitMQ-02
```

首次配置重跑的 `PLAY RECAP` 为：

```text
10.20.14.44 : failed=1
10.20.14.45 : failed=1
10.20.14.46 : failed=0
```

因此该阶段不能判定为 RabbitMQ 集群通过；首次日志中失败后产生的集群摘要是在旧错误传播逻辑下执行的，不作为验收证据。本次启动门禁重跑未产生后续 join 或管理配置摘要。
