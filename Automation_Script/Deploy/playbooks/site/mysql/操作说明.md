# MySQL 8.4.11 GTID 主从 + Keepalived 验收说明

## 部署内容

- 1 个 Primary、2 个 Replica，节点地址和 VIP 由现场配置提供。
- 使用 GTID 异步复制，Keepalived 仅在本机 MySQL 可写时持有 VIP；本方案不提供 Replica 自动提升。
- root、复制账号、VIP 验证账号和 VRRP 认证密码只从受控配置获取；VIP 验证账号仅允许 Primary 精确来源地址。

## 受控入口

从交付根目录执行正式入口；首次使用交互式向导录入 MySQL 的三节点拓扑后，可按组件范围部署或验证：

```bash
bash Automation_Script/Deploy/init_ansible.sh deploy --components mysql
bash Automation_Script/Deploy/init_ansible.sh verify --components mysql
```

`deploy` 会修改目标主机名、受管 hosts/inventory 块、软件和服务配置，执行前应具备 VM/磁盘快照和授权窗口。`verify` 不修改远端 MySQL 数据或服务配置，但会生成本地日志与 checkpoint。失败后可按相同组件范围重新执行。MySQL 初始化前会拒绝删除非空且未识别为 MySQL 的数据目录；常规入口不清空数据，也不提供事务回滚。

## 验收步骤

```bash
ansible-playbook -i inventory/hosts mysql/01_install.yml mysql/02_configure.yml mysql/03_replication.yml mysql/04_keepalived.yml mysql/05_verify.yml
ansible mysql -m shell -a "systemctl is-active mysqld keepalived"
```

使用现场凭据在受控终端确认 GTID、IO/SQL 线程、Replica `read_only` 和 VIP 状态。正式验证从 Ansible 管理节点检查 VIP 的 ICMP/TCP 可达性，再由 Primary 节点经 VIP 执行 SQL 角色确认；VIP 验证账号仅允许 Primary 精确 IP 来源访问，不使用 root 密码。模拟 Primary 故障时，确认 VIP 不会漂移到只读 Replica；随后按人工提升、fencing、复制重建流程恢复业务并记录时间。

## 风险边界

本方案提供固定 Primary VIP，不提供 Replica 自动提升或自动重建复制。GTID 异步复制存在未同步事务丢失风险；原 Primary 恢复后不得直接重新加入，通常需要 fencing、全量重建并重新建立复制关系。

人工恢复或重建必须先确认数据库备份、GTID 与复制线程状态、Primary fencing 结果和恢复责任人；不得将普通范围部署当作清空数据、自动提升或复制重建入口。
