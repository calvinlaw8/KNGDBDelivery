# RabbitMQ 4.2.9 集群验收说明

## 部署内容

- 3 个 Disk Node，种子节点和主机解析由现场配置提供。
- Erlang 必须固定为 26.2.5.13，禁止自动选择 27.x。
- Erlang Cookie 和管理员账号只从受控配置获取。

## 受控入口

从交付根目录执行正式入口；首次使用交互式向导录入 RabbitMQ 的三节点拓扑后，可按组件范围部署或验证：

```bash
bash Automation_Script/Deploy/init_ansible.sh deploy --components rabbitmq
bash Automation_Script/Deploy/init_ansible.sh verify --components rabbitmq
```

`deploy` 会修改目标主机名、受管 hosts/inventory 块、软件和服务配置，执行前应具备 VM/磁盘快照和授权窗口。`verify` 不修改远端队列数据或服务配置，但会生成本地日志与 checkpoint。失败后可按相同组件范围重新执行；常规入口不删除 RabbitMQ 数据目录，也不提供事务回滚。显式重建必须在网页工作台勾选 `deployment.rabbitmq_rebuild_cluster` 并完成危险操作二次确认。

## 验收步骤

```bash
ansible-playbook -i inventory/hosts rabbitmq/01_install.yml rabbitmq/02_configure.yml rabbitmq/03_verify.yml
ansible rabbitmq -m shell -a "rabbitmqctl cluster_status"
ansible rabbitmq -m shell -a "systemctl is-active rabbitmq-server"
```

确认集群包含 3 个 Disk Node、Management Plugin 正常、`guest` 已删除。生产消息队列应明确使用 Quorum Queue，并记录节点故障时生产和消费行为。

最终验证还会在种子节点通过 Management API 执行一次受控消息闭环：创建随机名称的临时 Quorum Queue，发布随机标记消息，使用 `ack_requeue_false` 消费并确认消息，再在 `always` 阶段删除临时队列。该队列不复用生产队列，管理员密码由 Ansible `uri` 模块传递并由 `no_log` 保护；闭环失败或清理失败都必须以失败证据为准，不能以服务 active 替代消息验收。

## 风险边界

Quorum Queue 丢失多数节点时不能继续假设集群可写。2 AZ 场景中，多数节点所在 AZ 故障会丧失 quorum。

RabbitMQ 4.2.9 使用 Khepri 时不支持 `rabbitmqctl force_reset`；该命令属于 Mnesia 旧路径，不能作为 Khepri 恢复手段。显式重建仅在网页工作台完成危险操作二次确认且 `rabbitmq_rebuild_cluster=true` 时执行。剧本会先按节点采集 systemd、Erlang node、Rabbit App、集群状态、Mnesia 目录元数据和近期 journal 的只读快照，再归档并校验 `/var/lib/rabbitmq/mnesia`（普通文件、权限 `0600`、`tar -tzf` 可读）。对响应正常、需要明确清空的节点，显式重建使用带 30 秒硬超时的 `rabbitmqctl stop_app` 后执行 `rabbitmqctl reset`，然后由种子节点先启动，其他节点按 `serial: 1` 依次 `join_cluster`。stop_app/reset 失败时只采集只读诊断并保持失败，不自动尝试其他恢复命令。普通健康集群加入路径不应套用这组破坏性命令。

`reset` 会删除该节点的用户、vhost、Management 元数据、集群身份和持久化消息；它不是事务回滚。显式重建前必须确认队列类型、消息持久化策略、事件责任人和可用快照，剧本会先归档 `/var/lib/rabbitmq/mnesia`。不得将普通范围部署当作清空队列数据或故障切换演练入口。
